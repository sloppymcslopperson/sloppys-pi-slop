S01

Canonicalize the status directory spelling

Board → status directories

Current text

“A fit board is a directory … consisting of the following child directories: open, closed, in_progress, backlog.”

Why clarify

The full spec uses in_progress, while the repository README’s short specification uses in-progress. Readers and tools can reasonably disagree about which directory name is valid.

Suggested clarification

State that the canonical directory names are exactly open, in_progress, backlog, and closed, with an underscore in in_progress. Hyphenated variants are not board statuses.

If alias handling is desired, keep it explicitly outside the spec: “Tools may accept in-progress as user input, but boards store in_progress.”

Effect: removes an observed contradiction without changing the directory model.

S02

State how normative language is used

Whole document

Current text

The spec mixes “may”, “by convention”, “should”, “recommend”, and declarative statements without defining which are requirements for a valid board.

Why clarify

A reader cannot tell whether an ignored “should” produces an invalid board, a warning, or merely a style preference. Implementation authors need that distinction.

Suggested clarification

Add a short conformance paragraph: MUST marks structural requirements for a valid board; SHOULD marks strong recommendations whose violation is allowed but noteworthy; MAY marks optional choices. Text marked “by convention” is a SHOULD unless stated otherwise.

Then use those terms consistently, and define “valid board” and “conforming board” once. This classifies existing statements rather than adding new obligations.

Effect: makes the existing rules testable and removes ambiguity about “ideally”, “recommend”, and “by convention”.

S03

Define what counts as a ticket file

Tickets

Current text

“A ticket is a markdown file within one of the aforementioned folders.”

Why clarify

“Markdown file” does not say whether .markdown counts, whether extension case matters, whether hidden files such as .gitkeep are tickets, or whether the spec document itself is a ticket. The spec also permits root-level FIT_SPEC.md.

Suggested clarification

Define a ticket as a file whose name ends in .md, located at any depth beneath one of the four status directories. Non-Markdown files, dotfiles such as .gitkeep, and Markdown at the board root (including FIT_SPEC.md) are not tickets.

State that a ticket’s identity is its board-relative path. Renaming or moving a ticket therefore changes its identity even though its content is unchanged.

Effect: gives tool authors one discovery rule and explains why exact paths matter.

S04

Clarify status versus project subdirectories

Board → subdirectories

Current text

“These subdirectories may be additional, more granular statuses, or directories specific to a particular overall ticket. If both are desired, directories specific to a project should be inside directories denoting status.”

Why clarify

“Status” and “project” directories are not distinguishable from the path alone, and the spec does not say whether a ticket’s status is the first segment or the full directory chain. That affects listing, moving, and validation.

Suggested clarification

State that the first path segment beneath the board is always the lifecycle status, and deeper segments are local organization (project, area, or finer status) defined by the board owner. A ticket’s lifecycle status is determined only by that first segment and cannot be overridden by frontmatter.

Add one example showing both layers, such as open/project-x/03-task.md and closed/project-x/03-task.md.

Effect: preserves the existing flexibility while making status unambiguous.

S05

Define ticket ordering precisely

Tickets → order

Current text

“Ticket order is determined by sorting the tickets by filename ascending.”

Why clarify

It is unclear whether ordering applies within a status, across the whole board, or across nested project directories. “Filename ascending” also leaves case sensitivity, locale, digit handling, and path tie-breaks unspecified.

Suggested clarification

Specify that ordering applies within each status directory, using a deterministic, locale-independent, case-sensitive comparison of the full filename. Compare the numeric prefix as text, not as an integer, so 02-… sorts before 10-… and 10-… before 9-….

For full-board listings, say that status grouping takes precedence and that the order between status directories is a presentation choice the tool should document. This avoids inventing a global priority order the spec does not currently define.

Effect: makes “priority” reproducible across languages and tools.

S06

Explain the priority prefix

Tickets → naming convention

Current text

“A ticket may be named anything. By convention, the name format is a two-digit number representing ticket priority … followed by an all-lowercase name …”

Why clarify

The spec never says whether 00 or 99 means highest priority, whether numbers above 99 are allowed, or whether a ticket without the prefix is still valid. Readers can infer opposite meanings from “priority” and “ascending”.

Suggested clarification

State that the leading number is a sort key, not a magnitude: smaller numbers sort first, so 00 is highest priority and 99 is lowest within the two-digit convention. Multiple tickets may share a number; the rest of the filename breaks the tie.

Reiterate that the prefix is convention only. A ticket without a numeric prefix remains valid and sorts by its full filename; tickets with other digit counts are nonconforming but not invalid.

Effect: removes the most likely source of misinterpretation while keeping naming optional.

S07

Limit frontmatter to descriptive metadata

Tickets → frontmatter

Current text

“A ticket may contain a frontmatter YAML header with arbitrary relevant information. It should not contain extraneous or frivolous information … A ticket without frontmatter is a valid ticket.”

Why clarify

The spec says frontmatter is arbitrary but does not say whether it may duplicate or override structural facts such as status, priority, or path, nor what exactly delimits it. Different parsers will disagree about malformed or unclosed headers.

Suggested clarification

Describe frontmatter as optional, descriptive metadata. When present, it is the first block whose opening and closing delimiters are lines containing exactly ---. An unclosed opening --- is body text, not frontmatter.

State that frontmatter is not authoritative for status, priority, filename, or ticket identity; those are derived from the path. Keys that duplicate structural facts are redundant, not overrides.

Effect: prevents “the file says closed but the directory says open” ambiguity.

S08

Make lifecycle transitions explicit

Lifecycle

Current text

“A ticket is created in open or backlog. It is moved to in_progress while it is being worked on. A ticket is moved to closed when it is finished.”

Why clarify

This describes a happy path but not whether transitions may be skipped, whether closed tickets may be reopened, or what “finished” means. The status of a ticket is also implied by directory placement but never stated as the sole source of truth.

Suggested clarification

State that the four directories are the four lifecycle states and that moving the file is the transition. New tickets MUST begin in open or backlog; a ticket is “finished” when a person decides its content no longer needs active work.

Allow direct moves between any states (for example, backlog straight to closed) and say that reopening a closed ticket means moving it back to open or backlog. That is a local decision, not a separate lifecycle state.

Effect: resolves skipped transitions and reopen behavior without adding new states or commands.

S09

Frame the body-length rule as guidance

Tickets → body

Current text

“The body of a ticket should be short, ideally no more then ~250 characters (3 lines long at 80 characters a line).”

Why clarify

The arithmetic is approximate (three 80-character lines is 240, not 250), “should” is undefined, and it is unclear whether the count includes frontmatter, whitespace, or Markdown syntax. Implementations may reject tickets the spec considers acceptable.

Suggested clarification

State that the guidance measures the body only, excluding frontmatter, and that ~250 characters is a readability target, not a validity rule. There is no hard maximum; tools may warn but must not reject a longer ticket solely for length.

Keep the rationale: short tickets are easier to scan, diff, and review in a file tree. Markdown formatting is allowed as long as the ticket remains understandable as plain text.

Effect: prevents valid tickets from being treated as malformed and clarifies what is being measured.

S10

Reconcile Git and archival options

Git

Current text

“A fit/ directory may be included in .gitignore. In this case, it is recommend that the time of completion is recorded, though it is not mandatory.”

Also: “A ticket that has just been closed should not contain the git commit hash of the commit that closed it.”

Why clarify

The two Git paragraphs describe different modes but do not say how they relate. The prohibition on a closing commit hash is unexplained, and “recommend” is weaker than the surrounding SHOULD-style guidance.

Suggested clarification

Make the two supported modes explicit: a tracked board, where ticket moves are committed alongside the work, and an ignored board, where the board is local. In the ignored mode, record a completion timestamp when closing, because Git will not preserve that event.

Explain that a closing commit hash is unnecessary and usually unknowable at the moment the ticket is moved; if a team wants traceability, a timestamp or an informational reference is enough. Archiving (zipping closed or compiling it into one file) is an optional external operation, not a board state.

Effect: turns two loosely connected notes into one coherent, optional Git story without changing the board layout.
