FIT Spec (Basic/Strict): Ten Fixes Before It Hardens

Thirty-nine lines now describe two systems, one of which is declared optional and unenforceable. These are the ten places where that costs a reader or a tool the most.

S11

Give “Strict” a definition that can fail

Strict → opening paragraph · extends v1 S02

Current text

“The strict FIT system is the basic system, with restrictions and specific rules. The system is intended to make the FIT system more suited to using collaboratively, automating, and checking programatically. It is entirely optional. Any variation of this spec is valid, as long as all contributors/coolaborates agree.”

“That is the extent of the basic system.”

Why it breaks

  • “Any variation of this spec is valid” is a global escape hatch. A board with two tickets in in_progress, no open directory, and a .txt ticket is still valid if the collaborators agree — so a checker has nothing to reject.
  • “Entirely optional” describes the choice to use Strict, but the text never says how a reader or tool knows a board claims Strict. There is no marker, revision number, or declaration.
  • The document never says what a violation means: invalid board, warning, or style note. “Should”, “may”, “must”, and bare declaratives sit side by side with no ranking.
  • The closing sentence of Basic (“That is the extent…”) reads as a guarantee that nothing further is required, which the next section immediately contradicts.

Suggested wording

Replace the paragraph with a conformance block. Proposed text:

“A basic-compliant board is a directory containing the four status directories, with Markdown tickets inside them. Basic-compliant boards may vary freely; the rules below are the only ones a checker may rely on.

A strict-compliant board is a basic-compliant board that also satisfies every rule in this section. Using the strict system is optional, but a board that claims it is bound by it: each rule is either required (violations make the board noncompliant) or recommended (violations are reported as warnings). Nothing outside this section is required, and behaviour not mentioned here is allowed.

Strict rules are versioned by this document; a tool that validates them should state the revision it implements.”

The superseded sentence becomes: “Basic boards need agree on nothing beyond this paragraph; the strict rules exist so that collaborators and tools can agree without negotiation.”

Effect: turns “strict” from a mood into a verifiable property, without forcing anyone to adopt it.

S12

Make Basic an actual subset of Strict

Basic and Strict → board and ticket sections · extends v1 S01, S04

Current text

“Structure: Somewhere, for example in a directory called "fit" in a repo, are four directories "open", "in_progress", "backlog", and "closed"”

“Tickets: Tickets are markdown files in one of the four afformentioned directories, or a subdirectory inside of one. Ticket order is determined by sorting the filenames ascending. Metadata is frontmatter, if needed.”

“A fit board is a directory called "fit" consisting of the following child directories (listed in sort order): - in_progress - open - backlog - closed”

“By convention, the "fit" directory lives at the root of a repository using FIT.”

Why it breaks

  • The two sections list the same four directories in different orders, and only Strict calls its list a sort order. A reader can reasonably conclude Basic prescribes a different order, or that order does not matter at all.
  • Basic permits the board directory to be named anything (“somewhere, for example… fit”); Strict says the board is a directory called fit, then one sentence later demotes the name and location to convention. Is the name required or not?
  • Strict repeats the ticket-definition and ordering sentences from Basic almost verbatim. Because they are presented as strict rules rather than restatements, they have already drifted (directory order, capitalization of “markdown”), and a future edit will drift them further.
  • Nothing says the relationship explicitly: strict-compliant implies basic-compliant, and the reverse does not hold. Without that, “strict is basic with restrictions” is only an assertion in a subtitle.
  • Basic's two paragraph-labels (“Structure:”, “Tickets:”) have no sentence punctuation and are not usable as citations, which makes it hard to say which Basic rule is being violated.

Suggested wording

Split the document into shared definitions plus two conformance profiles:

  • Terms (used by both): status directories, ticket file, ticket identity, ordering, and frontmatter are defined once. Basic and Strict then reference them rather than restating them.
  • Basic: “A basic board has the four status directories under one directory (any name or location) and Markdown tickets beneath them. Ticket order is the ascending sort of filenames within a status directory.”
  • Strict: “A strict board is a basic board that additionally names the board directory fit, follows the name template, and obeys the lifecycle and Git rules below. The location of fit at the repository root is a convention, not a requirement.”

State once, in bold: “Every strict-compliant board is basic-compliant. The converse does not hold.” Then delete the duplicated ticket/ordering sentences from Strict, and align both directory lists to the same order.

Effect: one definition per concept, no drift, and the Basic/Strict relationship becomes a testable implication instead of a subtitle.

S13

Bound the single-in_progress rule

Strict → Lifecycle · extends v1 S08

Current text

“A ticket may only be moved to "in_progress" if there are no tickets in "in_progress". If multiple tickets are in "in_progress", those tickets should be moved to other statuses until only one ticket remains in "in_progress". Git branches are the prefered way of handling the case where multiple tickets are being worked on simultanously.”

Why it breaks

  • No scope. Strict allows subdirectories with “more granular statuses”. Does in_progress/blocked/03-x.md count as a ticket “in in_progress”? Does “tickets in in_progress” mean directly inside it, or anywhere below it?
  • No resolution. When several are present, which one is allowed to stay? The rule says others “should be moved” but never says by whom or where. Two collaborators following the rule literally deadlock.
  • Branch ambiguity. A Git branch or worktree has its own board content. The “no tickets” condition is therefore true or false per checkout, not per repository — but the paragraph only mentions branches as an aside. A tool that checks the main checkout can report a violation that the branch rule permits.
  • Self-contradiction. The paragraph forbids what it then recommends: parallel work on branches is presented as the way to have multiple tickets in progress, yet the headline rule forbids more than one in progress.
  • Unclassifiable violation. “Should” is the only signal. Under Strict, is a board with two in-progress tickets invalid, warning-only, or fine?

Suggested wording

Replace with a scoped, required rule and a separate branch note:

“A board checkout has at most one ticket in in_progress. A ticket is in in_progress if it is anywhere beneath the in_progress directory, including nested status subdirectories.

The limit applies per working tree or branch, not per repository: branches may each have their own in-progress ticket, and a board on the main branch is not noncompliant because of a branch’s ticket.

Moving a ticket into in_progress while another is already there is a violation. The board becomes compliant again when one of them is moved out; choosing which is a local decision, and a checker reports the state rather than picking a winner. To work on several tickets at once, use separate branches or worktrees.”

Also state whether the initial state of a new board (zero tickets in progress) is the intended default — it is, so no exemption is needed.

Effect: one rule that a single checkout can check, with branches explicitly out of scope.

S14

Define a ticket, its identity, and nested statuses

Strict → Board, Tickets · extends v1 S03, S04

Current text

“A ticket is a markdown file within one of the aforementioned folders.”

“These directories may contain subdirectories. These subdirectories may be additional, more granular statuses, or directories specific to a particular overall ticket. If both are desired, directories specific to a project should be inside directories denoting status.”

“This specification document may live at the root of the board directory.”

Why it breaks

  • “Markdown file” does not settle .markdown, uppercase .MD, hidden files such as .gitkeep (needed to track empty status directories), symlinks, or attachments (screenshots, JSON fixtures) committed under a status directory. Each is either a ticket or not, and the text does not say.
  • The spec document is allowed at the board root, but nothing says it is not a ticket if someone places a FIT_SPEC.md inside a status directory. Under the current definition, it would be one.
  • Ticket identity is never stated. If identity is the path, renaming or moving changes it; if it is the frontmatter or the basename, duplicate basenames in open/project-a/ and open/project-b/ collide. Tools need the answer to address a ticket unambiguously.
  • “Status” and “project” subdirectories are indistinguishable from the path. Nothing says a ticket’s lifecycle status is the first segment under the board, so in_progress/blocked/03-x.md can be read as status blocked or as status in_progress within project blocked.
  • It never says the four status directories must exist even when empty, which is the first thing every checker tests.

Suggested wording

Add a short definition block:

  • “A ticket is a regular file whose name ends in lowercase .md, located at any depth beneath one of the four status directories, whose name does not begin with a dot. .markdown, .MD, dotfiles, and non-Markdown files are not tickets and are ignored by tools; a FIT_SPEC.md at the board root is not a ticket.”
  • “A ticket's identity is its path relative to the board root. Renaming or moving a ticket changes its identity. Duplicate basenames in different subdirectories are allowed because paths differ.”
  • “The status of a ticket is its first path segment beneath the board; deeper segments are local organization and never override status. Frontmatter never overrides status, priority, or identity.”
  • “The four status directories must exist, and may be empty. A status directory may contain nested subdirectories; a ticket may live directly in the status directory or in any of its subdirectories.”

Then the existing subdirectory paragraph follows naturally, with its example: open/project-x/03-task.md has status open and project project-x.

Effect: gives tools one discovery rule and one addressing rule, and makes “status” a path fact rather than an interpretation.

S15

Finish the name template

Strict → Tickets → naming · extends v1 S06

Current text

“A ticket is named according to following template: {two-digit ticket priority (0 high)}-{dash-seperated-short-name}.md”

“A ticket name should be shorter then 80 characters.”

Why it breaks

  • “0 high” contradicts “two-digit”. Is the highest priority 0- or 00-? If the template is two digits, the example must be 00; if 0 is legal, the template is not two-digit. Is 99 the lowest, and are 100 or -1 allowed?
  • No stated sort direction. “Priority (0 high)” plus “sorting ascending” implies smaller first, but a reader can equally read high numbers as high priority. Say it outright.
  • No character set, and the old lowercase rule vanished. “dash-seperated-short-name” does not say lowercase, ASCII, or which characters are permitted. The previous draft required all-lowercase; dropping that silently permits 03-Fix Typo.md.
  • “80 characters” is unmeasured. Including .md? Including the path? The stem only? Tools that warn on 80-character stems and tools that warn on 80-character full names will disagree.
  • No consequence. Strict says a ticket is named this way (required, in effect), but never says whether fix-typo.md is invalid, nonconforming-but-valid, or fine. Basic meanwhile allows any name, so the same file has two answers.
  • “according to following template” is missing an article, and the template braces are not explained as placeholders.

Suggested wording

“A strict ticket is named NN-name.md, where:

  • NN is exactly two digits, 00 through 99. 00 sorts first and means highest priority; 99 sorts last. Several tickets may share a number; the remaining name breaks the tie.
  • name is ASCII lowercase letters, digits, and hyphen-minus, with words separated by single hyphens.
  • The name excludes the extension from the limit and is at most 80 characters including NN- and .md; the path and parent directories do not count.”

Then add: “The prefix is a sort key, not a magnitude. A ticket whose filename does not match this template is nonconforming but still a valid ticket; it sorts by its full filename. Basic boards have no naming requirement.”

If 80 should be measured on the stem only (as tooling often does), say so explicitly and use one number everywhere.

Effect: one reproducible name format, one limit, and an explicit gap between “nonconforming” and “invalid”.

S16

Give ordering a scope and a collation

Basic and Strict → ticket order · extends v1 S05

Current text

“Ticket order is determined by sorting the filenames ascending.” (Basic)

“Ticket order is determined by sorting the tickets by filename ascending.” (Strict, restated)

“… child directories (listed in sort order): - in_progress - open - backlog - closed”

Why it breaks

  • Scope. Within a status directory? Across nested project directories? Across the whole board? For nested tickets, is the comparison against the basename or the relative path?
  • Collation. “Ascending” does not define case sensitivity, locale, Unicode normalization, or whether _, -, and digits compare as bytes or under a locale. “Ascending” in Swedish and in C produce different orders.
  • Digits. The naming template deliberately makes 02, 10, and 99 meaningful, but text sort and numeric sort differ as soon as a name has one digit (9-… sorts after 10-… as text). The spec relies on the text reading but never says so.
  • Ties. Two 00-fix-typo.md files in open/a/ and open/b/ compare equal by basename. Nothing defines a path tie-break.
  • Status order is only implied. Strict's list says “(listed in sort order)”, but Basic's identical set appears in a different order, and nothing says how a whole-board listing interleaves statuses. A tool cannot reproduce the spec's order from the text.

Suggested wording

“Tickets are ordered within each status directory by comparing their board-relative paths as sequences of Unicode code points, case-sensitively and without locale collation. Digits compare as text, so 02-… precedes 10-…, which precedes 9-… if such a name exists. When two tickets share a basename, the full relative path breaks the tie.

A whole-board listing groups tickets by status first, in this order: in_progress, open, backlog, closed; within a group, the path order above applies. A tool may offer other groupings, but its default must match this order.”

Then align Basic's directory list with this order (or label Basic's list explicitly as “a set, not an order”) so the two lists stop disagreeing.

Effect: any two implementations sort identically, and the status order becomes a rule instead of an aside.

S17

Define archiving without inventing a fifth status

Strict → Lifecycle · extends v1 S10

Current text

“Tickets in "closed" may be archived by being moved out of the "closed" directory.”

Why it breaks

  • Destination is undefined. Moved out to where? Outside the board (then it is no longer a ticket), into another status directory (then it is not archived, merely mislabelled), or into closed/archive/? Under Strict's own definition, a Markdown file in closed/archive/ is still a ticket with status closed — so that is not archiving at all.
  • It collides with the ticket definition. The whole point of archiving is that a ticket stops appearing in the board, but the only in-board place to put it is still inside a status directory, so every in-board move fails to archive anything.
  • Irreversible by omission. The sentence says “may”, but moving files out of the board is destructive for tooling and history; nothing says whether deleting a ticket is allowed, whether an archive must preserve paths, or whether a board with a missing closed directory remains valid.
  • It replaces a clearer rule. The previous spec named concrete archive operations (zip closed, or compile tickets into one Markdown file). Those disappeared, and the replacement is less precise than what it replaced.

Suggested wording

“Archiving is an operation on the board's history, not a lifecycle status. A board has exactly four statuses; a ticket in closed is complete whether or not it is later archived.

To archive, move the contents of closed out of the board — for example into a sibling directory, a zip file, or a single compiled Markdown file — and leave the closed directory in place. Archived files are no longer tickets under this spec. Deleting closed tickets instead of archiving them is allowed but loses their history.

An in-board subdirectory such as closed/archive/ does not archive anything: those files remain closed tickets and are still listed. If a board wants an in-board grouping, treat it as project organization, not archival.”

Keep archiving optional and exclude it from validity: an empty (but present) closed directory is compliant.

Effect: removes a rule that cannot be satisfied as written, and restores the concrete archive story the previous revision had.

S18

Enumerate the Git modes and their closing commits

Strict → Git · extends v1 S10

Current text

“A /fit directory may be included in .gitignore.”

“If a FIT directory is hidden via .gitignore, it may be its own git repository or a branch of the repository into which it is currently embedded. If it is tracked by a branch of the parent repository, the branch should be named "fit"”

“When a ticket is closed:”

“If the ticket is tracked by the same repository+branch that is tracking the work that was done, it should be included in the commit that finishes the work.”

“If the ticket is tracked by a different repository/branch, it may record the git commit that resolved the work, and the date that the work was completed, in the ticket's frontmatter. Neither are required.”

Why it breaks

  • Modes are never enumerated. At least four are possible: tracked inline on the work branch; ignored and purely local; ignored but checked out as a worktree on a fit branch; a separate repository. The text describes them piecemeal and never says which is the default or whether more than one may coexist.
  • “Hidden” and “tracked” are opposites. A worktree on a fit branch is normally excluded from the parent repository's tracking and listed in its .gitignore, yet the branch itself tracks the files. The paragraph treats “hidden via .gitignore” and “tracked by a branch of the parent” as disjoint when they are the same setup.
  • “When a ticket is closed:” is a dangling heading. It introduces no list and its two following paragraphs are separate conditional rules, not items under it.
  • Sequencing is missing. Moving a ticket to closed changes the working tree. In same-branch mode, is the move part of the work commit, or a separate commit? In worktree mode, the close must be committed on the fit branch — a rule the text never states, even though the following paragraph depends on it.
  • Metadata keys are unnamed. “the git commit” and “the date” have no field names, so two tools will write commit/completed and close_commit/finished respectively.
  • Requirements are unclear. “Should be included” and “may record” are the only signals; under Strict, a tracked board that closes a ticket in a separate commit is neither obviously compliant nor obviously violating.

Suggested wording

Replace the section with a short taxonomy and one rule per mode:

  • Inline tracked (default). The board is part of the repository. Closing a ticket changes open/… to closed/…, and that move is committed together with the work that completes it.
  • Local-only. The board is in the repository's .gitignore and is not versioned. No commit rule applies; recording completed in frontmatter is recommended so the closure survives.
  • Worktree on a fit branch. The board is ignored in the parent repository and checked out as a linked worktree on a branch named fit. Closing a ticket is committed on that branch, separately from the work branch.
  • Separate repository. The board is its own repository. Closing is committed there; the ticket may record the resolving commit and completion date.

Then: “In worktree and separate-repository modes, a closed ticket may carry commit and completed in frontmatter. Neither is required. In inline mode neither is needed, because the commit history already contains the move.”

Fix the prose: “A fit/ directory (a path relative to the repository root) may be listed in .gitignore” — the leading slash is gitignore syntax, not part of the name.

Effect: four concrete setups, each with an unambiguous closing procedure and shared metadata names.

S19

Make frontmatter descriptive, delimited, and non-authoritative

Strict → Tickets → frontmatter · extends v1 S07

Current text

“A ticket may contain a frontmatter YAML header with arbitrary relevant information. Any metadata must be immediately relevant to the reader of the ticket. A ticket without frontmatter is still a valid ticket.”

Why it breaks

  • No delimiters. A YAML header needs a start and end. Different parsers treat an unclosed opening --- as a header, as body, or as an error; the choose-your-own-answer version breaks round-tripping and writing tools.
  • “Arbitrary” versus “must”. The first sentence allows any relevant key; the second imposes a hard relevance requirement with no test. A checker cannot decide whether mood: tired is “immediately relevant”.
  • No authority rule. Nothing says frontmatter cannot declare status: closed inside open/, or priority: 00 that disagrees with the filename. Under the current text both are “arbitrary relevant information”, and a reader has two contradictory sources of truth.
  • Interacts badly with “The first line”. If frontmatter is present, is the “first line of the ticket” the first line of YAML, the first line after it, or the first non-blank body line?
  • No field names. The Git section already relies on recording a commit and a date; without reserved names, every implementation invents its own.

Suggested wording

“A ticket may begin with an optional YAML frontmatter block. The block starts on the first line of the file with a line containing exactly --- and ends at the next line containing exactly ---. If no closing delimiter is found, there is no frontmatter and the file starts with body text.”

“Frontmatter is descriptive metadata. It is never authoritative for status, priority, filename, or identity: those come from the path. Keys that duplicate those facts are redundant, not overrides, and a checker may warn about them. Frontmatter is intended for a reader of the ticket; keep it short and relevant.”

Reserve two optional keys for the Git rules: completed (date) and commit (resolving commit). Frontmatter does not affect ticket ordering or the first-line rule below.

Effect: deterministic parsing, one source of truth for structure, and interoperable completion metadata.

S20

Give the first line and body a testable shape

Strict → Tickets → body · extends v1 S09

Current text

“The first line of a ticket should be one to three sentences describing the issue.”

“Any additional sections must be preceeded by a sub-heading, and each additional section should have a single purpose and be kept short.”

Why it breaks

  • “First line” is ambiguous with frontmatter and with wrapped prose. A 140-character sentence is one line on one renderer and two on another; “one to three sentences” and “first line” cannot both be requirements.
  • “Describing the issue” narrows the medium. Tickets also record tasks, questions, ideas, and decisions. Calling all of them “the issue” is a small but persistent mismatch.
  • The two clauses disagree. “Additional sections must be preceded by a sub-heading” is required; “each additional section should … be kept short” is a soft recommendation. What is the unit of “additional”? Everything after the first sentence, or everything after the first heading?
  • Edge cases are unaddressed. A one-line ticket with no sections, blank lines before the first heading, nested headings, a heading as the very first body line, and a ticket with frontmatter and no body at all are all unspecified.
  • Body length disappeared. The previous revision's “~250 characters” guidance was the only measurable content target. Strict now has none, so a checker has nothing to warn on — even though the splitting intent was to make checking possible.

Suggested wording

“The body is everything after the frontmatter block. Its first paragraph should be one to three sentences stating the task, question, or issue. A body of one paragraph with no heading is valid.

If the body has more than one section, every section after the first paragraph must begin with a Markdown heading of level 2 or deeper, preceded by a blank line. Each section should cover one purpose and stay short.

As guidance rather than a validity rule, aim for a body of roughly 250 characters (three 80-character lines). There is no maximum; tools may warn about longer bodies but must not reject them for length. Frontmatter does not count toward the target.”

Effect: removes the line/sentence contradiction, covers one-line tickets, and restores a measurable target that was lost in the split.
