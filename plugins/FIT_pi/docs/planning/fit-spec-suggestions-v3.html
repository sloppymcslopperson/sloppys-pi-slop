FIT Spec v0.5: Ten Remaining Defects

Version 0.5 adopted most of the previous review and then introduced a few contradictions of its own. These are the ten that still cost a reader or a tool the most.

10 suggestions Reference IDs S21–S30 Spec text only Version 0.5 Spec commit 22982bf
What this reviews

Upstream FIT_SPEC.md at HeadEmptyNoNotes/FIT, commit 22982bf (“Refine and clarify FIT_SPEC.md”), which declares Version 0.5 (SHA-256 c2cc1a26…). This supersedes the Basic/Strict draft reviewed in fit-spec-suggestions-v2.html (IDs S11–S20). “Current text” is quoted verbatim; “Suggested wording” is proposal text, not an applied patch.

What v0.5 fixed from the last review
  • S11 conformance — now has required vs optional rules, explicit strict-implies-basic, and versioning. Fixed.
  • S12 Basic/Strict subset — now explicit, with “strict wins”. Fixed.
  • S13 single in_progress — now scoped to subdirectories and branch checkouts. Fixed.
  • S14 ticket definition — now .md-only, path-derived status, frontmatter non-authoritative. Mostly fixed; new archive hole.
  • S15 naming — now 00 high, two digits, lowercase, nonconforming-vs-valid. Mostly fixed; 30-char rule is broken.
  • S16 ordering — now gives status order, sub-status order, and a collation example. Partly fixed; multi-level shapes still undefined.
  • S17 archiving — now has a concrete archive.md format. Partly fixed; archive files become tickets.
  • S18 Git — now enumerates modes and fixes the dangling heading. Mostly fixed; sequencing still missing.
  • S19 frontmatter — now delimited, non-authoritative, with reserved keys. Mostly fixed.
  • S20 body shape — now has a summary paragraph and heading rule. Partly fixed; boundary and length guidance still absent.

Nine of the ten topics were acted on. The items below are the remaining gaps plus two defects the rewrite introduced: archive.md being a ticket (S21), and “required” rules coexisting with “valid tickets” that violate them (S22).

Suggestions, most consequential first

  1. S21 Exclude archive.md and board files from the ticket definition — definition

S21

Exclude archive.md and board files from the ticket definition

Basic → ticket definition ↔ Lifecycle → archiving · follows up v2 S14, S17

Current text

“A ticket is a markdown file (with the ".md" file extention), optionally containing frontmatter yaml, inside a status folder.”

“A closed ticket may be archived by appending its contents to an archive.md file within the 'closed' directory.”

“Status directories may contain .gitkeep files.”

Why it breaks

  • archive.md is a ticket under the definition. It is a Markdown file ending in .md, inside closed/, a status folder. So the archive container becomes a ticket: it appears in listings, participates in ordering, and competes for a unique name.
  • Every archived entry is also “inside” a ticket-shaped file but has no ticket file. Tools that enumerate tickets from the filesystem will see one file containing N tickets; the spec never says to parse it, or to hide it.
  • The ticket rules contradict the archive format. Strict tickets must have an NN- prefix and a lowercase name of 30 characters or fewer; archive.md satisfies none of that. Strict also says anything beyond a summary needs a heading, while archive.md has no summary and uses headings as record separators.
  • .gitkeep got an explicit exception, nothing else did. The same hole exists for a stray FIT_SPEC.md or STRICT placed in a status folder, editor swap files, and attachments (screenshots, fixtures) stored next to tickets.
  • Archived tickets removed from the board are called “valid tickets with a status of closed”, even though the definition requires a ticket to be inside a status folder. After removal, no such folder contains them.

Suggested wording

Replace the one-sentence definition with an explicit inclusion and exclusion list:

“A ticket is a regular file whose name ends in .md, located at any depth beneath one of the board's status directories, that is not one of the board's reserved files. Reserved files are: archive.md in a status directory, STRICT and FIT_SPEC.md at the board root, any file whose name begins with a dot (including .gitkeep), and any file with another extension. Reserved files are not tickets and are ignored by ticket listings, ordering, name uniqueness, and validation.”

Then say how archives relate to discovery: “An archive.md file is a container, not a ticket. Tools may list its entries as archived tickets, but entry headers are not filenames and do not participate in the board's naming rules. Archived tickets that have been moved out of the board are not discoverable by scanning the board; they are historical records.”

Keep the status-folder requirement for live tickets only, and drop the claim that removed tickets are “valid tickets” — call them archived records.

Effect: restores one discovery rule, stops the archive container from being treated as a malformed 00- ticket, and makes “removed from board” consistent.

S22

Separate “valid ticket” from “compliant ticket”

Strict → opening ↔ Tickets → priority, naming · follows up v2 S11, S15

Current text

“Rules are either required (violations make the board non-compliant) or optional (violations are reported as warnings). If something is not restricted here, then it is allowed.”

“A ticket's priority must be present, and must be two digits. … (”fix-bug.md“ is nonconforming and may cause issues, while ”00-fix-bug.md“ is conforming. Both are valid tickets.)”

“A ticket's filename must be lowercase.”

“Ticket names must not be duplicated within the FIT board”

Why it breaks

  • “Must” and “valid” are used for different subjects. The conformance model says violations make the board non-compliant, but the ticket rules say a file violating “must” is still a “valid ticket”. A reader cannot tell whether fix-bug.md is a valid nonconforming ticket, or evidence that the board is non-compliant, or both.
  • The terms are never defined. “Valid”, “conforming”, “compliant”, “nonconforming”, and “non-compliant” all appear; none is defined, and “conforming” vs “compliant” looks accidental. This matters because Strict says every required rule is binding.
  • “Required” and “optional” rules are not labelled. The framework classifies rules but the rules themselves never say which class they are in. Is lowercase required or optional? Is the 30-character limit required or optional (“should”)? A checker has to guess.
  • Uniqueness is a board-level required rule with a local remedy. “Names must not be duplicated” is absolute, then “the user should determine how to resolve the issue”. Two collaborators following the text can both be right.
  • “both are valid tickets” invites tools to accept anything. If a ticket can violate a required rule and remain valid, the word “must” is decorative — exactly the problem the v0.5 conformance section was added to fix.

Suggested wording

Add a short vocabulary block immediately after the conformance paragraph:

“A valid ticket is a file that satisfies the Basic definition; it is either a ticket or it is not. A conforming ticket is a valid ticket that also satisfies every required ticket rule in Strict. A compliant board contains only conforming tickets and satisfies every required board rule. A nonconforming ticket can exist in a non-compliant board; it is still a valid ticket, and tools should locate it but report the violation.”

Then label each rule: prefix required rules with “Required:” and optional ones with “Optional:” (or use a table of rule IDs). Rewrite the priority sentence as:

“Required: a strict ticket's filename begins with a two-digit priority, 00–99, where 00 sorts first. fix-bug.md is a valid ticket but a nonconforming filename; the board containing it is non-compliant.”

For uniqueness, say what happens on violation: “A duplicate name is a board-level violation. Tools report both files and do not choose a winner; the user resolves it.”

Effect: one vocabulary that makes “must” enforceable, and rule classes that a checker can implement without inference.

S23

The 30-character filename limit cannot work as written

Strict → Tickets → filename length · follows up v2 S15

Current text

“A ticket's filename name should be shorter than 30 characters (including extention and status). Going over this limit may cause display issues when rendering the ticket name in some tools.”

Why it breaks

  • “including … status” is self-defeating. The status alone can be longer than the whole budget: in_progress/ is 12 characters. Add 00- (3) and .md (3), and 12 of the 30 are gone before any name exists. A ticket in in_progress/blocked/ leaves almost nothing.
  • It is a 30-character limit masquerading as a filename limit. The text says “filename name … including extension and status”, three different measurements in one sentence. Tools must choose between the basename, the stem, and the board-relative path — and each gives a different pass/fail for the same ticket.
  • It conflicts with the naming template. The template asks for a “dash-separated-short-name”; after mandatory priority and extension, about 24 characters remain, and after a status segment, often 12–18. That is not enough for ordinary names such as fix-typo-in-readme (18) plus in_progress/.
  • The consequence is a display issue, not a validity rule. “Should” plus “may cause display issues” reads as optional, yet it shares a section with “must” rules and the 30 value looks normative.
  • It silently reverses the previous 80-character guidance without saying so, so tools and boards built against the earlier spec are now nonconforming for ordinary names.

Suggested wording

Pick one measurement and one purpose. Proposed text:

“Optional: keep a ticket's short name (the part after NN- and before .md) to 60 characters or fewer. This is display guidance, not a validity rule; tools may warn but must not reject a ticket. The filename's directory path and extension do not count.”

If a hard cap is actually wanted, state it as required and give the exact unit, for example: “Required: the board-relative path of a ticket is at most 120 characters, and the basename at most 60.” Do not mix status, extension, and name in one limit.

Either way, show one compliant and one noncompliant example, and state explicitly that the 80-character figure from earlier revisions is superseded.

Effect: one measurable limit that ordinary ticket names can satisfy, and no conflict with the template.

S24

Pin down identity, uniqueness, projects, and display names

Strict → Tickets → identity and naming · follows up v2 S14, S15

Current text

“A ticket's identity (name) is the short name within the filename. Ticket names must not be duplicated within the FIT board, and if such a case arises the user should determine how to resolve the issue (delete one, merge the two, etc). When displayed as a name and not a filename, the ticket's name should be in title-case with "-" replaced with " ".”

“Projects should be denoted within a ticket or its filename.”

Why it breaks

  • “Identity” is now the short name, not the path. That is a real design choice, but nothing says what happens to identity when the priority changes (same identity — good) or when the name changes (new identity). Tools that address tickets by path, name, or filename need the rule stated, and the relationship between identity and location is left implicit.
  • Uniqueness scope is undefined at the edges. “Within the FIT board” — does it include archive.md entries, tickets moved to a backup location, or tickets in closed? Can a name be reused after its ticket is archived or deleted? “Within the board” suggests not, but nothing says.
  • Projects were moved from subdirectories into “a ticket or its filename”. The previous revision allowed project subdirectories. Now subdirectories mean only sub-statuses, and a project must appear in the filename — which, combined with board-wide unique short names, forces project prefixes into every name. That deserves an explicit decision, not a “should”.
  • Title-case display is under-specified. What is the display name of 00-fix-2fa-login.md? “Fix 2fa Login”? “Fix 2FA Login”? What about digits, acronyms, and names that are already capitalized? A display rule that tools implement differently creates duplicate-looking names.
  • The uniqueness rule has no checker behavior. Required rule, user remedy, no statement that a tool reports duplicates rather than refusing to open the board.

Suggested wording

State the model in three sentences:

“A ticket's identity is its short name: the filename with the NN- prefix and .md extension removed. Identity is stable across priority changes and status moves; changing the short name is a rename and creates a new identity. The location of a ticket is its board-relative path, and tools that need a unique address use the path.”

For uniqueness: “Short names must be unique among tickets currently in the board, including archived entries recorded in archive.md. A name may be reused only after its ticket has been deleted or removed to a backup location; a warning should be reported when a reuse is detected.”

Replace the project sentence with an explicit choice, e.g.: “Projects are recorded in the short name (for example, 00-checkout-fix-tax.md) or in frontmatter; subdirectories under a status directory are sub-statuses, not projects.”

For display: “Display name = short name split on -, each segment capitalized, joined with spaces; digits and acronyms are left as written.”

Effect: one addressing rule, a testable uniqueness boundary, an explicit project convention, and a deterministic display name.

S25

Specify the STRICT marker and version rules

Document header, Strict → Board · follows up v2 S11, S18

Current text

“Version 0.5”

“Strict rules are versioned, and a tool that validates them should state the version being used.”

“A board is denoted as being in "strict" mode when it has a text file named "STRICT" at the root, containing the version string of the spec being used.”

Why it breaks

  • The version string format is undefined. Does the STRICT file contain 0.5, Version 0.5, v0.5, or 0.5\n? Is the filename case-sensitive (STRICT vs strict)? A checker cannot parse it from the text.
  • Behavior for unknown versions is unstated. A tool that implements 0.5 opening a board marked 0.6 or 1.0 has no instruction: validate what it knows, warn, refuse, or treat as basic? Same question for a malformed or empty file.
  • The version is duplicated. The document header says Version 0.5; the marker holds “the version string”; “strict rules are versioned”. Which one is authoritative, and what is the compatibility rule between 0.5 and 0.5.1?
  • Opt-in is one-directional. The text says how a board opts in; it never says that removing STRICT returns the board to basic (it should), or whether a basic board may contain a STRICT file for another reason.
  • “Should state the version” is the only tool requirement, and it is optional under the rule classification, so a validator may claim strict support without naming a version.

Suggested wording

“A board is in strict mode when it contains a file named exactly STRICT at the board root. Its content is the version string on a single line, exactly matching the version in this document's header (0.5), optionally followed by a newline. Removing the file returns the board to basic mode; it has no other effect.

A tool that validates strict mode must report the version it implements. If the marker's version is newer than the tool supports, the tool must report ‘unsupported strict version’ and must not report rule violations it cannot evaluate. A malformed marker is a required violation of the marker rule, not a reason to ignore the board.

Versions are major.minor. A tool supporting 0.x may validate any 0.y with a warning when y differs; a 1.x marker is unsupported until the tool declares support.”

Pick one source of truth: the header declares the current version, and STRICT records it.

Effect: one parseable marker, defined behavior for unknown versions, and a downgrade path back to basic.

S26

Ordering still misses several board shapes

Basic → ordering; Strict → Board → sub-statuses · follows up v2 S16

Current text

“Ticket ordering within the FIT board is status directory (in sort order specified above) -> sub-status directory by name ascending -> filename ascending. (An example of strings in ascending order: "00", "01", "10", "9", "B", "a", "b". Note the lack of a leading '0' on '9'.)”

“Basic-compliant boards may have additional status directories within the base board directory.”

“Subdirectories within top-level status directories may be sub-statues.”

Why it breaks

  • One sub-status level only. Basic defines a ticket's full status as “the '/'-conjoined directory names” — plural, arbitrary depth. Ordering names one “sub-status directory” then filename, so open/a/b/00-x.md has no defined position relative to open/a/01-y.md or open/b/00-z.md.
  • Tickets directly in a status directory have no stated position. Is open/00-a.md listed before or after everything in open/blocked/? The chain implies directory first, but a directory and a file are different kinds of nodes and the text does not say which comes first or whether a bare ticket counts as its own group.
  • Additional Basic status directories have no sort position. Basic explicitly allows them, but “sort order specified above” only names the four. Where does blocked/ or review/ go: alphabetically after closed, before in_progress, or somewhere user-defined? A whole board listing is unreproducible.
  • Collation is implied, not stated. The example shows B before a and 9 after 10, which implies code-point or byte order, but the text says only “ascending”. Locale, case, Unicode normalization, and _ vs - are unspecified.
  • Duplicates and archives. Basic permits arbitrary names and duplicates, so a tie-break is still needed at the Basic level; and where archive.md sorts is undefined (see S21).
  • “sub-statues” is a typo for “sub-statuses”, which matters in a normative sentence.

Suggested wording

“Tickets are ordered by their board-relative paths under a fixed traversal:

  • Status directories first, in this order: in_progress, open, backlog, closed. A basic board with additional status directories places them after these four, sorted by name.
  • Within a status directory, tickets directly inside it come first, sorted by filename.
  • Then sub-status directories, sorted by name, each traversed by the same rule recursively.

Comparisons are by Unicode code point, case-sensitive, with no locale collation or normalization; digits compare as text. The example "00" < "01" < "10" < "9" < "B" < "a" < "b" illustrates this. When two tickets would compare equal, the longer full path sorts after the shorter.”

This also settles where a bare open/00-a.md sits relative to open/blocked/01-b.md: before it.

Effect: a complete traversal that any two implementations can reproduce, including basic boards with extra statuses.

S27

Finish the archive mechanics and archived-ticket status

Strict → Lifecycle → archiving · follows up v2 S17

Current text

“A closed ticket may be archived by appending its contents to an archive.md file within the 'closed' directory. The format of the document is thus:”

### <file path including the 'fit' directory>
<contents as written in the .md file>
<intentionally-black line>

“Archived tickets may be moved from the board to a backup location. Archived tickets so removed from the board are still considered valid tickets with a status of "closed" for project history purposes, and an archive file may be moved back into the 'closed' status directory in the future. Note that the board's git history is not considered a reliable backup location.”

“The "closed" directory does not need to contain an "archive.md" file, it only exists when there are archived tickets present.”

Why it breaks

  • The append step does not say to remove the original. “Archived by appending its contents” produces a copy; if the original ticket file stays in closed/, the ticket exists twice — once as a file and once as an entry — and name uniqueness breaks immediately. If the original is removed, that must be stated, along with whether it is a move or a copy.
  • “intentionally-black line” is presumably an intentionally blank line, but the format is normative; a literal blank line and the literal words differ.
  • The heading format is under-specified. “file path including the 'fit' directory” — is it ### fit/closed/00-x.md or an absolute/relative path? Are the angle brackets placeholders? Is the path the record key, and may it repeat (two archived versions of the same ticket)?
  • Archived entries are not defined as records. Do they retain frontmatter? Does an entry count as a ticket for uniqueness, ordering, or validation? Can a user edit archive.md by hand, and is the file then required to remain valid Markdown?
  • “still considered valid tickets with a status of closed” contradicts the definition that a ticket is a file inside a status folder; once moved to a backup location, there is no status folder. It also makes the ticket “discoverable” in principle while not on the board.
  • Restoring is one sentence with no procedure. If archive.md is moved back into closed/, is it a container to be parsed or a giant ticket? If individual tickets are restored, where do they go and what happens to the archive entry?
  • No rule for ordering or display of archive.md relative to live closed tickets.

Suggested wording

“To archive a closed ticket, append one record to closed/archive.md and then delete the ticket file. A record is:

### <board-relative path of the deleted ticket>
<the ticket file's contents, including any frontmatter>

“The path is relative to the board root and begins with fit/; the header's blanks separate records. archive.md is a container and is not itself a ticket (see the ticket definition). Entries are historical records: they do not participate in ordering, and their names are not reserved for live tickets.

Archived records may be copied out of the board as a backup. They remain history, not board tickets; they have no live status. To restore one, copy its content into a new .md file under a status directory and remove the record. Moving archive.md back into closed/ is not a restore; a restored board must not contain archive.md as a ticket.”

Also decide whether hand-editing is allowed (yes, as Markdown) and whether a malformed record is a warning.

Effect: an archive operation with no duplicates, a parseable record format, and archived history that cannot re-enter the board as a ticket by accident.

S28

Close the frontmatter gaps

Basic → frontmatter; Strict → Git · follows up v2 S19

Current text

“A ticket's frontmatter must begin at the first line of the file, and be formatted as follows:”

- A line containing exactly "---"
- A block of valid YAML
- a line containing exactly "---"

“Frontmatter is metadata, and is non-authorative for data derived from the ticket's path (status, filename, identity, and priority).”

“Reserved frontmatter keys are:”

- "completed", containing the ISO 8601 date/datetime that a ticket was completed. Optional
- "commit", containing the commit hash of the commit that resolved the ticket, if the ticket is untracked. Optional

Why it breaks

  • Unclosed blocks are undefined. If the opening --- exists but the closing one never comes, is the file’s body parsed as frontmatter, as text, or is it invalid? Writers need a rule for the case where a user forgets the delimiter.
  • “Valid YAML” has no failure mode. Invalid YAML in an otherwise valid ticket: required violation, warning, or treated as body? The conformance model needs an answer.
  • Empty frontmatter is undefined. A pair of delimiters with no keys between them is syntactically a block but arguably not “a block of valid YAML”.
  • “if the ticket is untracked” conflicts with the Git section, which frames the same key as “tracked by a different repository/branch”. A ticket tracked on the parent’s fit branch is tracked, yet that is exactly the mode the Git section says may record commit. The condition should describe the board’s tracking mode, not an ambiguous “untracked”.
  • Key value formats are loose. “ISO 8601 date/datetime” allows 2026-11-08, 2026-11-08T12:00:00Z, and timezone offsets; “commit hash” does not say full or abbreviated. Tools that read these fields will disagree.
  • The angle-bracket conventions and list punctuation in the format block are inconsistent (quoted delimiters, lowercase “a line”, a stray space on the next line), and “non-authorative” is misspelled in a normative sentence.

Suggested wording

“Frontmatter is delimited by two lines containing exactly ---, the first on line 1 of the file. If no closing delimiter is found, the file has no frontmatter and the opening line is body text. The block between the delimiters may be empty and must otherwise parse as a YAML mapping. Invalid YAML is a required violation; tools must still show the ticket and must not treat the YAML as body.

Reserved keys: completed — an ISO 8601 calendar date (YYYY-MM-DD) or a full UTC timestamp with Z; commit — the full 40-character hash of the commit that resolved the work, recorded when the board is not tracked on the same branch as the work. Both are optional and may be absent.”

Add one example frontmatter block, and state that frontmatter never changes identity, priority, status, or location (already present).

Effect: deterministic parsing, a defined failure mode, and completed/commit values that all tools read the same way.

S29

Define where the summary ends, and restore body guidance

Strict → Tickets → summary and sections · follows up v2 S20

Current text

“A ticket may have a summary section at the beginning of its body (immediately following the frontmatter/at the first line if no frontmatter). The summary should be 1 to 3 sentences describing the purpose of the ticket.”

“Anything beyond the summary must have a sub-header ("### \<sub-header name\>") .”

Why it breaks

  • “The summary” has no end marker. Is it the first sentence, the first three sentences, the first paragraph, or everything before the first heading? A ticket with two introductory paragraphs is either one summary or a summary plus a section without a heading. The rule that anything beyond it “must” have an H3 is unenforceable until the boundary is defined.
  • Common body shapes are unaddressed. A short bullet list, a table, or a code block immediately after the summary: does each need an H3? A one-line ticket with no body: allowed (it says “may have a summary”)? A ticket whose entire body is a checklist?
  • H3 is hard-coded. “must have a sub-header ("### …")” forbids H2 (the more common top level) and makes the rule about presentation rather than structure. If the intent is “any heading”, say so; if H3 is intentional, say why and what H1/H2 mean.
  • The heading requirement is required, but reads as optional. The sentence says “must”, while the summary itself says “should”. Under the conformance model that is a required rule; it should be labelled as such and given a violation consequence.
  • Body-length guidance is still missing. v0.5 removed the old ~250-character target and did not replace it. The summary is now the only content rule, and it bounds the opening, not the ticket.
  • “summary section” vs “sub-header” mixes section terminology with headings; the escaped placeholder \<sub-header name\> plus a trailing space before the period reads like an unfinished edit.

Suggested wording

“The body begins after the frontmatter. Its summary is the text before the first heading, or the whole body if there is no heading; it should be one paragraph of one to three sentences stating the ticket's purpose. A ticket whose entire body is a single paragraph needs no heading.

If the body contains anything after that first paragraph, each such part must start with a Markdown heading of level 2 or deeper (## or ###). Headings must not skip a level. Lists, tables, and code blocks that belong to the summary may follow it without a heading; anything with its own topic gets one.

Optional: keep the whole body near 250 characters (about three 80-character lines). This is guidance; tools may warn but must not reject a longer ticket.”

Replace the escaped placeholder with a concrete example heading such as ## Notes.

Effect: a defined summary boundary, headings that match real Markdown, and a content target that survived the v0.5 rewrite.

S30

Fix the Git prose and close sequencing

Strict → Git · follows up v2 S18

Current text

“A "/fit/" directory entry may be included in the .gitignore of its parent repository. The use of "/fit/" and not "fit/" ensures that subdirectories of the parent project that happen to be named "fit" for some reason are not excluded”

“An FIT board that is untracked by its parent repository may be untracked by a git repository, or it may be tracked by its own indepdent git repository, or it may be tracked by a seperate branch of the parent repository (which must be named "fit").”

“When a FIT board is initialized within a project, by default it is tracked by the parent repository. This status may change at any time.”

Why it breaks

  • “may be untracked by a git repository” is ungrammatical and ambiguous: it presumably means “need not be tracked by any Git repository”. As written it says the board may be untracked by a repository, which is true of every file that is not in one.
  • Close sequencing is still missing for the fit-branch mode. Moving a ticket to closed changes the worktree on the fit branch, but the rule about “the commit that finishes the work” applies to the work branch. The text should say the close is committed on the fit branch, separately, before or after the work commit.
  • “By default it is tracked by the parent repository” has no operational definition. Default at initialization by a tool, by the user, or by the presence of a .gitignore entry? A board initialized outside a repository cannot be tracked by a parent at all.
  • The /fit/ advice only covers a board at the repository root. A basic board may live anywhere (the root board directory “be named anything”), and strict allows the board outside the repository entirely. In those cases the suggested ignore entry is wrong or irrelevant.
  • The two Git sections conflict on commit. Basic says the key applies “if the ticket is untracked”; Git says it may be used when tracked by a different repository/branch. Those overlap but are not the same condition.
  • The branch name is required (“must be named fit”) but the mode is described only for a board “untracked by its parent repository”. A worktree on fit is usually both excluded from parent tracking and tracked by that branch; the text never says the .gitignore entry is what makes those coexist.
  • Typos in normative text: “indepdent”, “seperate”, and the missing period after “not excluded”.

Suggested wording

“A board may be tracked inline by its parent repository (the default when initialized inside one), tracked by its own repository, or tracked by a separate branch of the parent repository named fit. It may also be kept entirely outside version control. The inline mode needs no special setup; the fit-branch mode requires the board path to be listed in the parent's .gitignore (for a board at the repository root, use /fit/).”

Then the closing rules, per mode:

  • Inline: move the ticket to closed and commit the move with the work in one commit.
  • fit branch / separate repository: commit the move on the board's branch or repository, separately from the work commit. The ticket may record commit and completed in frontmatter.
  • No version control: nothing to commit; completed is recommended so the date survives.

Define the default as “a tool that initializes a board inside a repository should track it inline unless asked otherwise”, and drop “this status may change at any time” (it is true of all Git state and adds nothing).

Effect: grammatical modes, a close procedure per mode, and consistent conditions for the commit key.
